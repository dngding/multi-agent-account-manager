# 机场订阅接入：Mihomo 固定本地端口

> 日期：2026-11-21
>
> 范围：Windows 叠号按账号代理的配置参考。本文没有修改或验收用户现有代理服务；示例中的订阅、节点和端口需要在独立测试实例中验证。

机场订阅链接不能直接填到叠号的代理输入框。由 Mihomo 解析订阅、连接机场节点，叠号只连接它在本机开放的 HTTP / SOCKS5 入口。

推荐先做两账号测试，确认链路后再扩到 10 多个账号：

| 账号 | 填入叠号的代理地址 | Mihomo 路由目标 |
| --- | --- | --- |
| 测试 A | `http://127.0.0.1:18081` | 已冻结配置的节点 A |
| 测试 B | `http://127.0.0.1:18082` | 已冻结配置的节点 B |

**不同本地端口不代表不同公网 IP。** 不同节点名称、服务器地址也可能共用出口；机场节点还可能负载均衡或更换出口。需要从每个账号的实际浏览器环境分别核验。机场订阅本身不保证独享或固定公网 IP。

## 1. 先准备独立测试环境

1. 使用独立目录和配置准备便携式 Mihomo 测试实例。不要覆盖原客户端配置，不停止现有代理、远控或其他生产服务。
2. 示例使用 `18081`、`18082`；使用前检查是否已占用。不要复用现有代理池端口。
3. 测试实例只监听 `127.0.0.1`，不启用 TUN、不设置系统代理，也不向局域网开放无认证入口。
4. 使用全新、未登录的测试 profile。叠号测试数据目录参见 [Windows 代理断线验收手册](windows-proxy-disconnect-acceptance.md)，不要复制生产 Cookie 或账号库。

只读检查示例端口：

```powershell
Get-NetTCPConnection -State Listen -LocalPort 18081,18082 -ErrorAction SilentlyContinue |
  Select-Object LocalAddress, LocalPort, OwningProcess
```

没有输出只表示查询时未发现监听；启动测试实例时仍应确认绑定成功。

## 2. 导入机场订阅

下面只是 `proxy-providers` 导入片段，**不是可直接上线的完整配置**。私有订阅 URL 应保存在本地私有文件中，不能提交到 GitHub、诊断日志或截图里。

```yaml
proxy-providers:
  airport:
    type: http
    url: "https://example.invalid/REPLACE_WITH_PRIVATE_SUBSCRIPTION"
    path: ./providers/airport.yaml
    interval: 3600
```

使用前确认：

- 订阅返回的是当前 Mihomo 版本能解析的 provider 节点 YAML。完整客户端配置、Base64 订阅、URI 节点列表不能直接视为同一种格式。
- 如需转换，使用本地受信客户端或本地工具；不要把私密订阅提交给第三方在线转换站。
- 上游认证、节点密码由 Mihomo 的私有配置处理。叠号当前代理字段只接受无内嵌认证的 `http://主机:端口` 或 `socks5://主机:端口`，不接受订阅 URL、路径、用户名/密码或 `https://` 代理协议。
- 订阅定时更新只更新导入内容，不等于账号出口已重新验收。

具体字段和入站能力以所用 Mihomo 版本及[官方配置文档](https://wiki.metacubex.one/)为准。

## 3. 为账号固定路由目标

### 建议先冻结两个节点配置

第一轮不要把账号指向自动测速、负载均衡、故障切换或手动共享选择器。先通过本地受信客户端选出 A、B 节点，将各自完整节点定义导出到**测试实例**的顶层 `proxies` 中，分别命名为 `muse-fixed-a`、`muse-fixed-b`。保留协议所需字段和认证参数，只调整本地名称。

节点导出由所用客户端完成，本仓库目前没有订阅解析或节点导出器。不要手工猜测节点参数，也不要将导出的密码提交仓库。冻结配置后，后续订阅更新不会自动替换这两个静态定义；节点到期、上游变更或配置失效时需要重新确认。冻结的是配置，不保证机场公网 IP 不变。

在确认这两个名称是该实例可解析的固定节点后，才加入以下入站片段：

```yaml
listeners:
  - name: muse-a-in
    type: mixed
    listen: 127.0.0.1
    port: 18081
    proxy: muse-fixed-a

  - name: muse-b-in
    type: mixed
    listen: 127.0.0.1
    port: 18082
    proxy: muse-fixed-b
```

`mixed` 入口可接收 HTTP / SOCKS5；表中的叠号配置统一使用 HTTP。`proxy` 字段必须在目标版本中得到正确解析，并经真实请求证明确实指向指定节点；不能只看端口已监听。

### 直接使用 provider 节点或筛选组时的限制

不同版本对 provider 动态节点的解析、`listeners[].proxy` 可引用目标以及代理组空集的处理可能不同。本文不提供未经验证的“订阅正则筛选为单节点组”完整配置，也不承诺零匹配时一定报错。

如改用只包含一个节点的组，必须确认以下情况全部会明确失败：

- 节点被订阅删除或更名，筛选结果为空。
- provider 下载失败、缓存缺失或启动时尚未加载。
- 节点无法连接、认证失败或上游中断。

任何上述情况都不能选择 `DIRECT`、兼容直连目标、其他机场节点或共享默认出口。若当前版本不能证明这一点，继续使用已导出的固定节点，并把自动订阅绑定留作后续开发。

**叠号目前只保存代理 endpoint，不读取 Mihomo 的订阅和节点名称。** 它不能直接发现“节点名消失后代理客户端换了目标”。节点绑定有效性需由 Mihomo 配置校验及运维检查保证；程序中的握手检查不能替代这项验证。

## 4. 校验后再填写叠号

先针对测试配置运行 Mihomo 的配置检查，二进制路径和配置路径按本地实际情况替换：

```powershell
.\mihomo.exe -t -f .\config.yaml
```

配置检查成功只说明配置可被该版本接受，不证明固定路由、出口独立或断线行为合格。启动独立测试实例后，再依次确认两个端口、具体节点和实际请求。

在叠号中，将相应地址保存到对应账号的代理设置，并在**首次打开和登录前**完成绑定：

```text
Test A -> http://127.0.0.1:18081
Test B -> http://127.0.0.1:18082
```

当前功能分支的 Windows 新增窗口支持“仅保存”和“检查并打开”：可以先仅保存为待配置账号，不创建或预热网页；填写代理后由手动打开触发预检，成功后才激活。最终源码 `4dce77d` 的 [Windows CI](https://github.com/dngding/multi-agent-account-manager/actions/runs/44915899771) 已全部成功：Rust 测试 23/23，格式日志无 `Diff`，独立 EXE / NSIS 均构建成功。`e3ec4d2` 独立 EXE 已从空目录实测空代理打开被阻止、仅保存无 profile / 不预热、保存代理后仍待激活及手动打开激活。最终 `4dce77d` EXE 已完成最小回归：恢复两账号、清空 A 代理后关闭 A 并阻止重开且 B 保留，重启后 A 仍无浏览器、B 经原代理恢复；详见[本轮状态验收报告](windows-proxy-setup-state-acceptance-2026-11-21.md)。这些结果均限合成未登录 profile 与本地 HTTP CONNECT 场景；新增全流程在 `e3ec4d2` 上完成，不能视为已在最终 EXE 全量复测。提交 `86679ef` 的旧验收版本没有这项新增流程，使用它测试时仍应依照验收手册预置空白数据。

对于已有账号，修改代理会关闭旧视图；若它是当前活动账号且新配置有效，会重新检查并重建，其他账号不因此立即打开。待激活账号保存代理后仍需手动打开。Windows 新账号必须使用代理，旧账号保存代理后也会保持这一要求；清空代理会关闭会话并阻止打开，直到重新配置。只有未曾转为必须使用代理的兼容旧账号，才保留原有系统默认网络行为。

本机可用下面的命令做端口链路冒烟检查。公网地址及响应不要放进公开日志：

```powershell
curl.exe --proxy http://127.0.0.1:18081 --connect-timeout 10 --max-time 20 https://api.ipify.org
curl.exe --proxy http://127.0.0.1:18082 --connect-timeout 10 --max-time 20 https://api.ipify.org
```

这只验证对应 `curl` 请求，不能代替账号 WebView2、登录弹窗、DNS / WebRTC / IPv6 流量验证。若两个响应相同，应按共用公网出口处理；不同响应也只代表检查时刻，仍需关注漂移。

## 5. 两账号验收后再扩容

| 场景 | 必须观察的结果 |
| --- | --- |
| A、B 正常打开 | 请求分别通过预期本地端口和固定节点；实际浏览器出口与记录一致 |
| 停止 A 的本地入口 | A 被关闭、再次打开被阻止，B 可继续使用 |
| 保留 A 本地入口，令 A 上游失效 | A 请求失败，不换到 B、其他节点或直连；B 可继续使用 |
| A 节点被删除或更名 | 配置或绑定检查明确失败，不能自动换目标 |
| A 上游恢复 | 重新检查后才允许 A 打开，仍绑定原目标 |
| 重启测试实例和叠号 | A、B 端口映射和固定节点绑定保持 |

“停止本地入口”和“上游失效但入口仍在”是两个不同故障，必须分别测试。当前叠号的代理握手和后台复核属于应用层保护；本地入口仍可握手、实际浏览器请求却失败的情况，也需要记录并检查。故障时不能通过清空账号代理或临时改成 `DIRECT` 继续操作。

本仓库已有两个未登录 profile 使用本地 HTTP CONNECT 代理的[公开页面实机记录](windows-proxy-acceptance-results-2026-11-21.md)。[本轮状态验收](windows-proxy-setup-state-acceptance-2026-11-21.md)进一步在 `e3ec4d2` 验证后台 A 断线后自动显示中断卡片、B 保留，恢复代理后 A 可再打开；最终 `4dce77d` EXE 的清空代理、缺代理重开阻断、B 保留和重启恢复最小回归已完成。测试程序、两条代理及 scoped WebView 已退出，测试数据已清理，生产配置哈希与目录状态前后一致。两轮记录都没有验证本文的真实机场订阅配置、SOCKS5 实机链路、生产登录账号、完整出口、DNS / WebRTC 或系统级 fail-closed。

两账号全部通过后，按 2 → 5 → 10 多账号增加固定端口与绑定记录。每增加一个账号都要重新核验其实际出口。固定端口可以降低误绑概率，但不能提供设备隔离、清除历史账号关系，或保证平台不会关联账号。
